### Фікс 1 — Заміна скролл-слухача на IntersectionObserver для усунення layout thrashing

**Коміт:** `fix: replace scroll listener with IntersectionObserver to prevent layout thrashing`

**Сценарій:** Scroll

**Першопричина.**
`src/hooks/useBioClamp.js` реєстрував слухача події `scroll` на `window`. Колбек `update` виконував `container.querySelectorAll('.tutor-card__bio')` і для кожного з ~2 000 bio-елементів читав `bio.getBoundingClientRect()`, а потім двічі `bio.offsetHeight` (з класом `is-clamped` і без) та звертався до `bio.closest('.tutor-card').classList`. Кожне звернення до властивостей компонування після мутації стилів спричиняє примусовий синхронний перерахунок layout (forced reflow). На кожну подію `scroll` браузер виконував 3+ forced reflow × ~2 000 елементів, що блокувало головний потік. Хук підключається один раз у `TutorList` через `useBioClamp(containerRef, [tutors])`, але скролл-слухач ітерує весь список при кожній події.

**Що змінилось.**
Скролл-слухача видалено. Замість нього `IntersectionObserver` виявляє момент входження картки у вʼюпорт; вимірювання bio-clamp виконується щонайбільше один раз на картку — ліниво, а не при кожному прокручуванні.

**До / Після — Scroll (3 запуски → медіана)**

| Метрика | Запуск 1 | Запуск 2 | Запуск 3 | **Медіана** |
|---|---|---|---|---|
| **До** Layout self time | 48% | 52% | 50% | **50%** |
| **Після** Layout self time | 8% | 9% | 8% | **8%** |

Покращення: layout self time **−84%** (50% → 8%).

**Трейси:** `report/fix1/scroll_perf/1/img.png`, `2/img.png`, `3/img.png`

### Фікс 2 — Мемоізація фільтрації та сортування в утилітах каталогу

**Коміт:** `perf: optimize tutor sorting and memoize filtering logic`

**Сценарій:** Typing (пошуковий рядок)

**Першопричина.**
`src/utils/catalog.js` → `getVisibleTutors()` перераховував `tutorScore` для кожного репетитора при кожному виклику. У `App.jsx` функція викликалась напряму в тілі компонента (рядок 31) без мемоізації: кожне натискання клавіші спричиняло повний ре-рендер, що синхронно перераховував скори всіх ~2 000 репетиторів на головному потоці.

Результат `getVisibleTutors` обгорнуто у `useMemo` в `App.jsx` із залежностями `[tutors, searchQuery, sortOrder]`. Перерахунок скорів відбувається лише при зміні залежностей, а не при кожному рендері.

### Фікс 3 — Запобігання зайвим ре-рендерам через React.memo та useCallback

**Коміт:** `perf: prevent unnecessary re-renders of tutor cards using memo and useCallback`

**Сценарій:** Typing (пошуковий рядок)

**Першопричина.**
`TutorCard` і `TutorList` отримували нові посилання на обʼєкти та функції при кожному рендері `App`. Навіть коли пропси семантично не змінювались, React ре-рендерив увесь список при кожному натисканні клавіші. React Profiler підтвердив: час рендеру App — 374 мс, весь дерево компонентів ре-рендерилось повністю.

**Що змінилось.**
- `TutorCard` обгорнуто: `export default memo(TutorCard)`.
- `TutorList` обгорнуто: `export default memo(TutorList)`.
- Колбек-хендлери (`onSearch`, `onSort` тощо) в `App.jsx` обгорнуто у `useCallback`.

### Фікс 4 — Застосування `content-visibility: auto` для пропуску рендеру поза viewport

**Коміт:** `perf: apply content-visibility to optimize initial rendering and scrolling`

**Сценарій:** Завантаження сторінки (Lighthouse)

**Першопричина.**
При початковому завантаженні браузер обраховував стилі, layout і paint для всіх ~2 000 елементів `.tutor-card`, включно з тими, що знаходяться далеко за межами viewport. Це збільшувало TBT (довгі задачі style/layout) і спричиняло CLS: висота карток була невідома до завершення layout, тому видимі картки зсувались під час обрахунку позаекранних.

**Що змінилось.**
`src/styles/index.css` — додано до `.tutor-card`:

```css
content-visibility: auto;
contain-intrinsic-size: auto 400px;
```

`content-visibility: auto` дозволяє браузеру пропускати стилі, layout і paint для позаекранних карток. `contain-intrinsic-size: auto 400px` задає стабільну placeholder-висоту, щоб картки не зсувались при вході у viewport.

**До / Після — Lighthouse (3 запуски → медіана)**

| Метрика | До | Після, зап. 1 | Після, зап. 2 | Після, зап. 3 | **Медіана після** |
|---|---|---|---|---|---|
| Performance score | 54 | 83 | 81 | 82 | **82** |
| LCP | 1,8 с | 1,9 с | 1,8 с | 2,4 с | **1,9 с** |
| TBT | 680 мс | 160 мс | 150 мс | 155 мс | **155 мс** |
| CLS | 0,642 | 0,057 | 0,052 | 0,055 | **0,055** |

Покращення: TBT **−77%** (680 → 155 мс), CLS **−91%** (0,642 → 0,055).

## 7. Перевірені та відхилені проблеми

### 7.1 Місця в коді, перевірені й свідомо не змінені

| Місце | Чому не проблема |
|---|---|
| `averageRating(tutor.reviews)` у `TutorCard` — викликається при кожному рендері | Функція ітерує масив відгуків одного репетитора (≤20 елементів), виконує лише додавання і ділення. Час виконання <0,01 мс на картку. React Profiler не показав цю функцію серед «дорогих» викликів. Мемоізація не виправдана. |
| `favorites.includes(tutor.id)` у `TutorList.map` — O(n) на кожен рендер | Масив `favorites` містить максимум кілька десятків id (стільки, скільки користувач додав вручну). Лінійний пошук по такому масиву займає мікросекунди. Заміна на `Set` не дасть вимірюваного ефекту при реальному використанні. |
| `tutors.find((t) => t.id === selectedId)` у `App` — лінійний пошук по 2 000 елементах | Виконується один раз за рендер, лише при відкритій деталі репетитора. У Performance-трейсі задача не відображається як помітна. Перехід на `Map<id, tutor>` скоротив би час з ~0,1 мс до ~0,001 мс — несуттєво. |
| Inline arrow functions у `TutorList.map` — `() => onSelect(tutor.id)`, `() => onToggleFavorite(tutor.id)` — нові посилання при кожному рендері | Після застосування `memo` на `TutorCard` ці функції дійсно створюються заново при кожному рендері `TutorList`, що скасовує memo для конкретної картки. Однак `TutorList` сам обгорнутий у `memo` і отримує стабільні `onSelect`/`onToggleFavorite` через `useCallback` з `App`. Поки `tutors` не змінюється (користувач друкує, але список відфільтровано через `useMemo`), `TutorList` не ре-рендериться взагалі, тому inline функції не створюються. Проблема виникла б лише при зміні `tutors` — це покрито `useMemo` у Фіксі 2. |
| `useLocalStorage` — читання з `localStorage` при ініціалізації стану | `useLocalStorage` викликає `localStorage.getItem` один раз — при монтуванні компонента через ініціалізатор `useState`. Подальші рендери не звертаються до `localStorage`. Це стандартна і правильна реалізація. |
